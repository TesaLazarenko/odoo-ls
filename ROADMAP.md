# Роадмапа odoo-ls (форк)

Стан на 2026-11-28, гілка `integration-1.7.0-memory`.
Що вже злито в гілку, описано в [changelog.md](changelog.md).

Пріоритети:
- **P1** — може зламати сервер або дає помітно хибний результат.
- **P2** — бракує можливостей, на які очікує користувач LSP.
- **P3** — неточності аналізу в рідкісних випадках.

Кожен пункт описано за схемою **проблема → як вирішити → критерій готовності**.
Позначка «не перевірено» означає, що пункт знайдено читанням коду, але не відтворено.

## P1

### 1. `todo!()` у хуку `__get__` (не перевірено)

**Проблема.** `PythonArchEvalHooks::eval_get` (`server/src/core/python_arch_eval_hooks.rs:1080`)
викликає `todo!()`, коли до функції з хуком `EvalGet` звертаються через клас, а не через
екземпляр (`ContextKey::ParentInstance == false`). Це паніка, яка, ймовірно, зупиняє весь сервер.
Хук ставить `update_get_eval_func_level` на функції `__get__`.

**Як вирішити.** Відтворити тестом. Для звернення через клас повернути сам дескриптор
(клас поля), як це робить Python, замість паніки.

**Готово, коли** тест зі зверненням через клас проходить без паніки, а hover показує тип дескриптора.

### 2. `env.ref()` не повертає тип запису

**Проблема.** Хук `ref()` (`python_arch_eval_hooks.rs:1489-1493`) лише перевіряє, що xml_id
існує (OLS05001), і повертає `None`. Через це після `self.env.ref('module.xml_id')` немає
автодоповнення і перевірки полів. Крім того:
- не враховуються xml_id, оголошені в CSV;
- не перевіряється, чи модуль xml_id є в залежностях поточного модуля;
- форма `base.model_<name>` (записи `ir.model`) не підтримується.

**Як вирішити.** Брати модель із запису XML/CSV (`model=` у `<record>`, назва файлу CSV) і
повертати екземпляр цієї моделі. Додати перевірку залежностей так само, як для `env['model']`.

**Готово, коли** `self.env.ref('base.main_company').` пропонує поля `res.company`, а xml_id з CSV
і з модуля поза залежностями дають очікувані діагностики.

## P2 — середовище

### 3. ✅ Python-інтерпретатор із Docker-контейнера

Зроблено, опис у [server/docs/python-env.md](server/docs/python-env.md), код у
`server/src/core/python_env.rs`.

**Що було.** `python_path` — одна команда без аргументів, тож `docker exec` не задати;
шляхи `sys.path` контейнера відкидались перевіркою `is_dir()` на хості; інтерпретатор
запускався двічі на кожному старті.

**Що зроблено.**
- Ключ `python_command` (командний рядок, має пріоритет над `python_path`) і
  `path_mappings` (`container_path=host_path`), у CLI `--python-command` і `--path-mapping`.
- Один probe-виклик замість двох (версія, `EXTENSION_SUFFIXES`, `sys.path` і вміст його каталогів),
  також для локального інтерпретатора.
- Для `docker exec`/`podman exec` каталоги `sys.path` без відповідника в `path_mappings`
  копіюються один раз на образ у `<cache>/odoo-ls/python-env/images/<image id>/`: через `tar`
  у контейнері без `__pycache__`, `*.pyc` і пакета `odoo` (його сервер бере з `odoo_path`),
  скомпільовані розширення стають порожніми заглушками. Якщо `tar` в образі немає, копіюється
  через `docker cp`. Копія атомарна (тимчасовий каталог і перейменування), копії образів, на які
  не посилається жоден кеш, видаляються.
- Середовище кешується за командою й зіставленнями разом з ID образу.

**Вимога до швидкодії — виконано.**
- Інтерпретатор у контейнері запускається лише на першому старті з новим образом:
  один probe і один `tar` на каталог `sys.path`. Під час запитів — ніколи.
- Повторні старти викликають лише `docker inspect` (перевірено strace: жодного `docker exec`).
- Файли бібліотек читаються з копії на хості, без звернень до Docker.
- Якщо контейнер зупинений або Docker недоступний, береться кеш.

**Заміри** (образ Odoo 18.0, `dist-packages` 1.5 ГБ, з них `odoo` 1.3 ГБ; `--parse` модуля,
що імпортує бібліотеку, встановлену лише в контейнері):

| Інтерпретатор | Час | Імпорт бібліотеки з контейнера |
|---|---|---|
| локальний `/usr/bin/python3` | 0.96 с | `OLS02001 ctronly not found` |
| `docker exec`, перший старт (probe + копія 85 МБ) | 1.47 с | розв'язано |
| `docker exec`, наступні старти | 0.96 с | розв'язано |
| `docker exec`, контейнер зупинено (кеш) | 0.96 с | розв'язано |

Через `docker cp` замість `tar` перший старт тривав 24 с, бо потік містив 1.4 ГБ.

**Тест:** `core::python_env::tests::docker_environment_is_probed_once_per_image` із
заглушкою `docker`, яка рахує виклики: перший старт — 1 probe і 1 `tar`, повторний — 0,
новий образ без `tar` — probe і `docker cp`, Docker недоступний — кеш, без кешу — помилка.

**Що лишилось:**
- [ ] `docker compose exec <service>` не розпізнається (команда працює, але без кешу й копій;
  треба знайти контейнер через `docker compose ps -q` з тими ж `-f`/`--project-directory`).
- [ ] Odoo й addons мають бути на хості: з контейнера беруться лише каталоги `sys.path`.

## P2 — можливості LSP, яких сервер не оголошує

Сервер (`server/src/server.rs`, `ServerCapabilities`) зараз оголошує hover, declaration,
definition, completion, references, document/workspace symbols і semantic tokens (лише full).

- [ ] **Rename** — перейменування поля, методу чи моделі разом із посиланнями в Python, XML і CSV.
  Можна побудувати на основі наявного `references`.
- [ ] **Code actions** — швидкі виправлення для діагностик: додати модуль у `depends`,
  виправити опечатку в назві поля чи моделі.
- [ ] **Signature help** — аргументи методів ORM і полів під час виклику.
- [ ] **Go to implementation** — усі перевизначення методу через `_inherit`.
  Пов'язане: type hierarchy для моделей, call hierarchy.
- [ ] **Inlay hints** — тип записів для `env['...']` і результатів методів ORM.
- [ ] **Code lens** — «N перевизначень» над методом моделі.
- [ ] **Document highlight**, **folding ranges**, **document links** (шляхи в `__manifest__.py`).
- [ ] **Semantic tokens range/delta** — зараз токени завжди рахуються для всього файлу.
- [ ] **Pull diagnostics** (`textDocument/diagnostic`) — зараз діагностики лише надсилає сервер.
- [ ] **Форматування** — найнижчий пріоритет, для Python це вже роблять ruff і black.

**Готово, коли** можливість оголошено в `ServerCapabilities` і покрито тестом у `server/tests`.

## P3 — неточності аналізу

- [x] **Generic-типи.** Зроблено, опис у [server/docs/generics.md](server/docs/generics.md),
  код у `server/src/core/generics.rs`. Аргументи типу (`list[Item]`, `dict[str, Item]`) несуться
  обчисленням і підставляються в методи, індексацію й цикли; бази `Generic[...]`/`Protocol[...]`/`List[...]`
  більше не дають хибного OLS01001 (28 в Odoo 19, `ControllerRegistry` у `rabbitmq`); працюють
  `Optional`, `X | None`, `type[X]`, узагальнені функції й конструктори, PEP 695.
  Лишилось:
  - [ ] об'єднання кількох типів (`A | B`) не моделюються: без звуження за `isinstance`/`match`
    виклики перевірялися б на кожному з них (хибні OLS01009 на ключах `cryptography` в Odoo 20);
  - [ ] ParamSpec, TypeVarTuple, межі TypeVar, `Callable[..., R]`, `Literal`;
  - [ ] декоратори, що змінюють сигнатуру (`decorator.decorator`: OLS01007 у `rabbitmq/rabbit/controller.py`).
- [ ] **Кілька можливих значень.** Коли за виразом стоїть кілька функцій, виклик не
  валідується (`evaluation.rs:816`). Для моделі береться лише перший символ (`evaluation_utils.rs:78`).
- [ ] **Розпакування `*`** у присвоєннях не розбирається (`evaluation.rs:1654`).
- [ ] **Поля `Properties`.** Шляхи через них у доменах пропускаються без перевірки (`evaluation.rs:1881`).
- [ ] **Умови `sys.platform`** не обчислюються, тому аналізуються обидві гілки
  (`python_arch_builder.rs:994`). Умови з `sys.version_info` вже враховуються
  (`_check_sys_version_condition`), і з Docker-інтерпретатором — за версією Python контейнера.
- [ ] **Модулі з однаковою назвою** в різних шляхах addons не розрізняються (`symbols/manifest_create.rs:29`).
- [ ] **Структура файлу (document symbols)** не показує змінні з walrus-оператора (`:=`)
  в умовах і змінні з шаблонів `match/case` (`features/document_symbols.rs:199, 210, 249`).

**Готово, коли** для кожного пункту є тест, який падав до виправлення.
